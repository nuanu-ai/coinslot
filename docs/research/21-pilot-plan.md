# План до пилота: Freeland продаёт через x402

Прикидка крупными этапами (2026-08-26, обсуждение с Дмитрием). Принцип —
ходячий скелет: узкий вертикальный срез, но все основные компоненты
существуют как настоящие начальные прототипы, без ручных костылей. Нужен
кабинет — он есть, просто тонкий.

## Компоненты, которые обязаны существовать к пилоту

Гейтвей (402-край, карточки, цены со снапшотом и хуком, машина заказов,
очередь, квитанции — один Postgres); SDK мерчанта с воркером и CLI verify;
кабинет-минимум (карточки, настоящая кнопка паузы, список заказов и
квитанций — та самая «сводка продаж», которой не поверил владелец-ридер);
песочный покупатель (наш агент полного цикла); экспозиция в каталог
(инфраструктура coinslot.nuanu.ai готова со спайка); адаптер Freeland
(воркер их инженера поверх их API); портал документации (есть, догоняет
реальные имена по мере кода).

## Этапы

**Этап 0 — решения и каркас.** Принять ADR-0001 (экспозиция через Bazaar;
условие «успешный settle» выполнено) и правку п. 3 ADR-0002 — оба ждут
слова Дмитрия. Поднять монорепо по ADR-0003: contracts (zod-схемы карточки,
заказа, хука, квитанции — контракты портала становятся кодом), core
(машина состояний как чистая логика), каркасы gateway и sdk, CI зелёный.
Старт этапа — отдельное решение Дмитрия: с первым продуктовым кодом
активируется ритуал сдачи из хартии.

**Этап 1 — вертикальный срез: покупка у мок-мерчанта.** Гейтвей отдаёт
402 в тестовой сети, песочный покупатель проходит полный цикл: нашёл
карточку → цена → платёж → заказ через очередь → наш собственный
SDK-воркер выдал → settle → квитанция. Синхронный режим целиком, verify
v0 (полнота карточки + прогон идемпотентности). Мерчант пока мы сами, но
через те же интерфейсы, что получит Freeland, — ни одного шага руками.
Ворота: песочная покупка зелёная от начала до конца.

**Этап 2 — все режимы денег, кабинет, бой.** Асинхронный режим полностью:
accepted / deliver / refuse, пометка «требует возврата», сроки, повторы,
цена продажи в заказе, id котировки. Кабинет v0: вход по ключу, карточки
с настоящей паузой, заказы и квитанции. Разделение песочницы и боя:
тестовый контур + помеченные тестовые заказы + переключение в основную
сеть. Листинг в Bazaar с coinslot.nuanu.ai, мы сами — первый мерчант в
проде со смоук-товаром. Ворота: продукт целиком существует в прототипах,
продаёт в бою нам самим.

**Этап 3 — пилот Freeland.** Выбор одного-двух реальных товаров с их
инженером (кандидаты: аренда номера — синхронный; eSIM — асинхронный;
динамические цены — их хук или адаптер). Пре-регистрация предсказаний
трения → передача инструментов → инженер интегрируется сам → verify
зелёный → тестовая покупка → листинг → настоящие продажи (первые — наши
помеченные, дальше ждём органику). Обратная связь по методу хартии:
дневник трения, интервью, счёт против пре-регистрации. Ворота = ответ
пилота: можем ли мы сделать это технически хорошо.

## Что сознательно не в пилоте

Режим с подтверждением (ручных мерчантов в пилоте нет — механика остаётся
в машине состояний, включим с первым таким мерчантом); автоматика
возвратов (состояние и журнал есть, исполнение по инциденту — политика
«продаём повторновыдаваемое» держит случай редким); webhook и курсорный
транспорты заказов (воркера достаточно); дополнительные каталоги;
white-label домены; редактирование карточек в кабинете (SDK хватает);
подписки и продление (backlog №11).

## Хостинг этапов 1–3

Ядро — резидентный процесс (подписки воркеров, консьюмер очереди,
последовательность вокруг платежа), поэтому serverless-платформы класса
Vercel ему не подходят по форме, а не по вкусу — обсуждено с Дмитрием
2026-08-26. Деплой: существующая VM (coinslot.nuanu.ai, Caddy, compose) +
GitHub Action «пуш в main → сборка → деплой» — верселевский DX без смены
формы. Портал раздаёт тот же Caddy. Триггеры пересмотра названы заранее:
публичный портал с трафиком или нужда в preview-деплоях → статика на
Vercel; второй инцидент ручной возни с VM → managed-платформа резидентного
класса (Fly/Railway/Render).

## Открытые вопросы техрешения, закрываемые по ходу этапов

Авторизация management API и воркера (этап 1 — минимум, ключ; подпись
хука — к этапу 3 по требованиям Freeland); числа сроков и SLO свежести —
до этапа 3; контакт для старта разговора — до любого показа портала
наружу.
