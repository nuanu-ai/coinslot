# Спайк: путь листинга витрины в x402 Bazaar

Ветка: `spike/bazaar-listing`, код в `spikes/bazaar-listing/`. Начат 2026-08-25.
Цель: запротоколировать полный цикл «листинг → изменение → делистинг» для
провайдера, экспонирующего множество мерчантов, и выяснить, что автоматизируемо.

## Механика Bazaar (из доков CDP + живого API, 2026-08-25)

**Листинг — не процедура, а side effect.** Формы подачи и админки нет. Запись
в каталоге появляется, когда:

1. эндпоинт отвечает `402` с корректным блоком `extensions.bazaar`
   (описание ≤500 символов, JSON Schema входов, пример выхода, цена, сети);
2. через CDP facilitator проходит **первый успешный оплаченный вызов**
   (settle с `paymentPayload.resource`).

Инструменты:
- TS: `@coinbase/cdp-sdk/x402` → `createX402Server` (авто-декларирует
  discovery); `declareDiscoveryExtension` из `@x402/extensions/bazaar`.
- Валидация без API-ключа: `POST https://api.cdp.coinbase.com/platform/v2/x402/validate`
  — проверяет достижимость, 402, bazaar-блок, приемлемость для фасилитатора.
- Чтение каталога без ключа: `GET .../v2/x402/discovery/resources`
  (15 202 записи на 2026-08-25).

**Изменение**: правишь метаданные у себя — витрина подтягивает; quality/ranking
пересчитываются раз в 6 часов. Точная задержка обновления метаданных в доках
не специфицирована → замерить в Phase 1 (вопрос: обновляется ли запись только
при новом settle?).

**Делистинг** — только пассивный:
- 30 дней без settle → удаление;
- серия проваленных health-probe → авто-делистинг;
- эндпоинт перестал отдавать 402 → «eventually removed».
Активного API «снять листинг» нет. Opt-out — не декларировать discovery
extension (собирать сервер из `@x402/*` напрямую, минуя `createX402Server`).

## Ответы на вопросы спайка

**Автоматизация листинга N мерчантов — да, тривиальна.** Phase 0 показал:
мерчант = запись в `catalog.json`, ресурсы и 402-метаданные генерируются из
конфига. Bootstrap-вызов (триггер каталогизации) — скриптуемый self-call.
Ручных шагов: ноль.

**Управление витриной — это управление своим сервером.** Смена цены/описания =
деплой конфига. Сложность низкая; вся операционка — держать эндпоинты живыми
(health-probes!) и следить, чтобы по каждому ресурсу был хотя бы один settle
в 30 дней (иначе авто-вылет). Для платформы это значит: нужен «пульс» — либо
органический трафик, либо периодический self-settle ($0.001 комиссии после
бесплатной 1000/мес).

**Non-custodial из коробки:** `payTo` задаётся per-ресурс → деньги идут
напрямую агент → кошелёк мерчанта, Coinslot денег не касается. Вопрос
монетизации платформы (нет нативного сплита в x402) — отдельный, в backlog.

## Журнал

  `X-PAYMENT` (без верификации, честно помечено).

- Оговорка: wire-формат воспроизведён по наблюдаемым данным; в Phase 1
  заменить самописный 402 официальным middleware и свериться.

### Находки Phase 1: x402 v2 и поведение валидатора

Wire-формат v2 (specs/x402-specification-v2.md, transports-v2/http.md):
`x402Version: 2`; обязательный заголовок `PAYMENT-REQUIRED` (base64 всего
PaymentRequired-объекта — каноническое место в HTTP-транспорте); `resource`
уехал из `accepts[]` в top-level объект `{url, description, mimeType,
serviceName?, tags?}`; в `accepts[]` — только платёжные поля (`amount`, не
v1 `maxAmountRequired`); сети — CAIP-2; для POST/PUT/PATCH обязателен
`bodyType`; клиентский заголовок теперь `PAYMENT-SIGNATURE` (бывший
`X-PAYMENT`); `bazaar.schema` — полноценная JSON Schema 2020-12 над всем
`info`, фасилитатор валидирует по ней.

Эмерджентные требования (не из текста спеки, из поведения):
1. **402 обязан отвечать на любой метод листингового пути** — валидатор и
   краулеры ходят только GET; paywall, привязанный к одному методу, делает
   POST-ресурсы невидимыми (22/25 fail до фикса). Реальный метод объявляется
   в `bazaar.info.input.method`.
2. Validate принимает недокументированное поле `method`; список чеков
   динамический — появляются условные чеки (`…method.matches_request`),
   которых не видно на проходящем GET-ресурсе.
3. Спека показывает пустое тело `{}` (всё в заголовке), но валидатор CDP
   читает и тело → отдаём и заголовок, и тело (belt-and-braces).
4. **`serviceName`/`tags` молча режутся** при не-ASCII или превышении длины
   (32 симв., ≤5 тегов) — кириллическое имя мерчанта тихо исчезло бы из
   выдачи. Для платформы это значит: своя валидация мерчант-метаданных
   обязательна.
5. Заглушечный `payTo` (0x…dEaD) проходит simulation — валидация проверяет
   форму и приемлемость для фасилитатора, не деньги. Листинг всё равно
   случается только после реального settle через CDP facilitator.

План: официальный middleware → `validate` → первый settle → замер задержки
появления в discovery → изменение цены/описания → замер задержки обновления.

### Находки Phase 1 (продолжение): официальный стек и первый settle

Интеграция `@coinbase/cdp-sdk` 1.55.0 + `@x402/*` 2.23.0 (валидация осталась
25/25 на всех ресурсах; поддельная подпись получает отказ фасилитатора — verify
настоящий). Кошельки спайка: buyer `0x6D21…4872` (3 USDC), seller
`0x784d…d1aC` (payTo); ключи только в `.env` на VM.

Технические находки:
- **`self_send_not_allowed`**: фасилитатор CDP запрещает платежи payer==payee.
  Следствие для продукта: «пульс» листингов нельзя делать self-send'ом с
  одного кошелька — нужен отдельный кошелёк-пульсатор.
- **v2 прячет вердикт в заголовок**: тело 402 всегда `{}`; причина отказа —
  только в base64 `PAYMENT-REQUIRED.error`, причём заголовок один и тот же для
  «заплати» и «платёж отвергнут». Клиент, не читающий его — слеп (наш был).
- `wrapFetchWithPayment` бросает исключение на клиентских ошибках, но
  **молча возвращает 402** при серверном отказе.
- **Скрытый потолок $1/платёж** в дефолтных spendControls x402Client — SKU
  дороже $1 умирает до подписи, без предупреждения.
- Таксономия ошибок фасилитатора: `…payload_signature` (подпись),
  `…authorization_value` (сумма), `contract call failed / execution reverted`
  (on-chain симуляция = «нет денег»), `self_send_not_allowed`.
- `extra.{name,version}` обязательны для EIP-3009-подписи и должны хэшироваться
  в DOMAIN_SEPARATOR токена; ошибка всплывает только на фасилитаторе.
- Сервер `createX402Server` **падает на старте**, если фасилитатор недоступен —
  витрина умирает от чужого аутэйджа; для продукта нужен retry/degrade.
- SDK всегда инжектит `builder-code` (ERC-8021 атрибуция Coinbase) в
  extensions EVM-маршрутов, без опции отключения.
- `resource.url` за TLS-терминатором собирается как `http://…` + query —
  обязателен `trust proxy` + пиновка канонического URL.
- Операционное: сеть VM перехватывает DNS `api.cdp.coinbase.com`
  (индонезийский провайдер блокирует Coinbase) — обход через DoH в
  entrypoint. Жёсткое ограничение для деплоя в этой локации.

### Первый settle — 2026-08-25

- 10:53:24Z: оплата `/freeland/esim/plans` 0.001 USDC, buyer `0x6D21…4872` →
  payTo `0x784d…d1aC`; tx
  `0x291381619e27c783fbc66bd2b359bee6f89dbf95b7bdda035de7f90e2f2eec5e` (Base).
  Полный цикл 402→подпись→verify→settle→фулфилмент: ~2.1 с.
- 10:53:27Z (**+3 секунды**): `validate.index` = `{active: true,
  lastCrawledAt: …}` — краулер Bazaar проиндексировал ресурс немедленно.
- 10:57Z: полный обход выдачи discovery (15 145 записей) — в *выдаче* нас ещё
  нет. Гипотеза: попадание в выдачу — после пересчёта ранжирования (до 6 ч).
  Ежечасный мониторинг запущен; latency зафиксируем.
- Параметры фильтрации discovery API (`search`, `q`, `resource`) игнорируются
  — проверка присутствия возможна только полным обходом.
- **≤11:05Z (замер: ≤12 минут от settle): ресурс появился в выдаче discovery**
  (каталог 15 145 → 15 146). «До 6 часов» из доков — про пересчёт
  ранжирования/позицию, а не про попадание в выдачу.
- **Листинг — per-resource, не per-domain**: в выдаче только оплаченный
  `/freeland/esim/plans`; три неоплаченных ресурса витрины в каталог не
  попали. Следствие для платформы: bootstrap-settle обязателен для КАЖДОГО
  SKU — «тестовая покупка» входного гейта должна прогоняться по всем SKU
  мерчанта, а пульс поддерживать каждый листинг отдельно.

**Итог Phase 1: полный путь пройден.** Мерчант-конфиг → публичная витрина →
официальная валидация → реальная оплата агентом → запись в Bazaar: суммарно
один день, из них путь «settle → видимость в каталоге» — ~12 минут.

### Phase 2 — делистинг (после Phase 1)

Остановить 402 на одном ресурсе, провалить health-probes на втором → замерить
«eventually removed». 30-дневное окно неактивности целиком не ждём —
фиксируем документально.

## Чего не хватает продукту, замерено против спайка (2026-08-27)

Спайк прошёл валидацию 25/25 — но прошёл её **спайковый сервер**, а не наш
шлюз. В `apps/` и `packages/` слова `bazaar` нет ни разу. Замер на живом
стенде: платёжный вызов, который отдаёт наш шлюз, несёт ключи `x402Version`,
`error`, `resource`, `accepts` — блока discovery нет. То есть сегодня наш
ресурс в витрину не попадёт, и это не «сделано плохо», а «не начато».

Хорошая новость в том, что почти все данные для блока у нас уже есть, и они
лежат в карточке. `declareDiscoveryExtension` из `@x402/extensions/bazaar`
хочет пример входа, JSON Schema входа и пример выхода; в карточке это `params`
(из которого схема выводится, как её уже выводит контракт) и `result`.
Описание и заголовок тоже там. Значит блок — это проекция карточки, такая же
по природе, как публичная витринная проекция, а не новая подсистема.

Что действительно надо решить, а не вывести:

- **Канонический URL ресурса.** SDK по умолчанию собирает его из запроса, и за
  обратным прокси это даёт `http://` и тащит query-строку в идентификатор.
  Пинить из `PUBLIC_BASE_URL`, который у нас уже есть в конфигурации.
- **`serviceName` и `tags`** — полей под них в карточке нет. Фасилитатор режет
  их по printable ASCII, ≤32 символа, ≤5 тегов, так что своя проверка
  обязательна. Это изменение контракта и решение о том, чьи это поля:
  мерчанта или наши.
- **Фасилитатор на пилоте — CDP**, потому что каталогизация идёт по settle
  через него (ADR-0001). Сегодня умолчание — `https://x402.org/facilitator`,
  а стенд стоит в песочнице.

Порядок работ и приоритет относительно находок внешнего обзора —
за Дмитрием.

## Длина описания: что удалось замерить (2026-08-27)

Ограничение «описание ≤500 символов» выше взято из доков CDP, а не из
наблюдения. Попытка подпереть его данными: пройдена одна страница живого
каталога, `GET /platform/v2/x402/discovery/resources?limit=100`, 100 записей
из 14 823. Самое длинное описание — 468 символов; ровно 500 нет ни одного,
длиннее 500 — ни одного, в диапазоне 490–500 — ни одного. Пагинация по этому
эндпоинту за одну страницу не сдвинулась (курсор в ответе не нашёлся под теми
именами, что пробовались), поэтому выборка — 0.7% каталога и одна страница.

Что это значит: данные не противоречат ограничению и не подтверждают его.
Жёсткая обрезка оставила бы записи, стоящие ровно на границе, — таких нет.
Сама граница не проверена: у нас нет публичного https-ресурса, на котором
можно было бы отдать описание длиннее 500 и посмотреть на ответ. Число
принято в контракт (`DescriptionSchema`, ADR-0012) как прочитанное, а не как
измеренное.

## Размер заголовка с декларацией: замер (2026-08-27)

Challenge несёт декларацию одним заголовком, и заголовок растёт вместе с
картой. Замер на сборке без потолков: описание 55 символов и один параметр —
1,9 КБ; описание 1 500 символов и восемь параметров — 4,3 КБ; описание 4 000
символов и сорок параметров — 10,3 КБ. Потолок описания в 500 символов
закрывает второй и третий размер по линии описания и ни один — по линии
параметров: карта с сорока параметрами достигает того же порядка при описании
глубоко внутри лимита. Что делает конкретный прокси с заголовком такого
размера — не замерено; предел такого рода проявится как транспортная ошибка,
а не как отказ, который можно прочитать.
