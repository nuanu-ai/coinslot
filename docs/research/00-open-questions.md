## Техрешение этапа 1 (закрываем по ходу)
- [x] Имя и форма заголовка ключа → зафиксированы в contracts
      (`MERCHANT_KEY_HEADER`, `merchantKeyHeaderValue`, `merchantKeyFrom` в
      `packages/contracts/src/api.ts`); гейтвей и SDK импортируют один
      источник, drift ловит тест api.test.ts
- [x] Сборка публикуемых пакетов → есть. `tsc` собирает `@nuanu-ai/coinslot` и
      `@nuanu-ai/coinslot-contracts` в `dist` — JS плюс декларации рядом; бандлер не
      заводили, потому что исходники и так импортируют друг друга через
      `.js`-спецификаторы, которые `tsc` переносит как есть. Внутри монорепо
      ничего не поменялось: `exports` по-прежнему указывает на `src`, а на
      сборку его подменяет `publishConfig` в момент упаковки, — правка видна
      без компиляции. `bin` объявлен там же, поэтому `npx coinslot verify`
      стартует. Проверяет это `pnpm outside`: удаляет `dist`, пакует тарболы
      (сборку делает `prepack`, так что путь тот же, что у релиза), ставит их
      npm-ом в каталог вне репозитория и гоняет там импорт и `verify` —
      с заведомо неполной карточкой как контролем. Перед первой публикацией эта
      же проверка компилирует импорт в чужом strict TypeScript-проекте с
      `skipLibCheck: false`, стандартными Web API Node 24 и без ambient-пакетов
      из рабочего дерева. Публикацией управляет Changesets, public-доступ задан
      и пакет `0.1.0` выпускается тегом `sdk-v0.1.0` через отдельный workflow
- [x] Работает ли `verify` по ключу, без файлов → нет, и это решение, а не
      недоделка. Такой проверке нечего проверять: карточка попадает в
      `list_merchant_cards` только пройдя `CardSchema` на публикации, а
      `checkCard` гоняет ту же схему, — то есть проверка по построению всегда
      отвечала бы «полно» и учила бы мерчанта верить зелёному, которое ничего
      не значит. Беcключевой запуск при этом полезен сам по себе: он работает
      до того, как у мерчанта появился ключ и что-то опубликовано.
      Пересматриваем, когда появится маршрут пробной публикации: он проверял бы
      то, чего локальная проверка не может, — отказы, которых нет ни в одной
      схеме (`packages/sdk/src/check-card.ts`)
- [ ] Тестовый путь для идемпотентности verify: нет маршрута, поднимающего
      заказ по своей карточке для теста, и нет способа сделать `Order.test`
      истинным без живого платежа — verify v0 честно останавливается на этой
      половине
- [x] Как SDK читает ответ с незнакомым словом → остаётся строгим; каждое новое
      значение, которого старый читатель не знает, сначала двигает версию
      контракта. Старый worker останавливается на handshake до получения заказа
      (ADR-0006 п. 3)
- [ ] Какие наши сроки мерчант обязан видеть или называть сам. Сегодня три
      числа ведут себя по-разному без принципа, который бы их разделял:
      `fulfill_deadline_seconds` необязателен и подставляется из настроек
      шлюза, `confirm_deadline_seconds` устроен так же, а синхронный бюджет
      карточкой не выражается вовсе. Мерчанта при этом держат по всем трём, и
      по первому он может оказаться должен возврат по часам, которых не видел
      ни он, ни агент. Сделать одно из трёх обязательным — оставить два
      молчаливых умолчания и одно громкое; это решение уровня ADR, а не правка
      схемы
- [ ] Параллелизм подписки воркера (имя параметра и умолчание) — портал сам
      держит их нерешёнными
- [ ] Отказывает ли Bazaar в листинге из-за POST-пробы. Первый настоящий
      вердикт `pnpm smoke:listing` (28.08.2026, против живого
      `https://coinslot.nuanu.ai`, до этого проверка честно отвечала «вердикта
      нет»): по обеим карточкам GET-проба **принята** и прошла всё
      обязательное — 402, x402 версии 2, заголовок `PAYMENT-REQUIRED`, схема
      `exact`, сеть `eip155:84532`, USDC, сумма, `payTo`, `maxTimeoutSeconds`,
      и целиком разобралось discovery-расширение Bazaar. POST-проба по обеим
      **отклонена**: валидатор шлёт POST с пустым телом, а покупка без тела —
      это 400, потому что открывать заказ нечем (`routes.ts`, `purchase`).
      Так и задумано: GET существует ровно для краулеров, POST — это покупка.
      Чего мы не знаем: считает ли сам листинг обязательным, чтобы платный
      ресурс отвечал 402 на любой метод. Если да — выбор из двух, и оба
      неприятны: либо 402 выдаётся до разбора тела (тогда агента зовут платить
      за запрос, который потом всё равно откажут — ровно то, чего мы избегаем
      на паузе карточки), либо мы объявляем в discovery только GET и живём с
      отклонённой пробой. Мерить на живом листинге, а не рассуждать
- [ ] Экономика bootstrap-покупки. Листинг в Bazaar — per-resource и только
      после settle (спайк 04), а платёж non-custodial: тестовая покупка,
      которой мы листингуем SKU, отправляет мерчанту его собственную цену с
      нашего кошелька-покупателя. Для пилотных SKU это центы; для дорогого
      SKU входной гейт «тестовая покупка» становится платой за листинг из
      нашего кармана. Варианты не выбраны: покупать по настоящей цене и
      считать это стоимостью привлечения; договорной возврат; спец-цена
      bootstrap-вызова (риск расхождения с ценой в декларации — надо мерить,
      сверяет ли Bazaar settle с заявленной ценой). Решение за Дмитрием,
      когда появится первый мерчант с дорогими SKU.
- [ ] Индексирует ли Bazaar settle в тестовой сети, или в выдачу попадает
      только mainnet. Единственный измеренный листинг (спайк 04) — Base
      mainnet; Base Sepolia не пробовали ни разу, а умолчание шлюза —
      именно она. Инструмент для замера написан: `pnpm smoke:bootstrap`
      делает bootstrap-покупку и потом обходит каталог discovery, и его
      вердикт «settled, not yet listed» — это и есть данные по этому
      вопросу, а не поломка. Ответ решает, можно ли листинговать пилот с
      тестовой сети или каждый SKU стоит настоящих денег с первого дня.
      Конфигурация будущего публичного тестового канала сама этот вопрос не
      разделяет: она сочетает Base Sepolia с публичным тестовым фасилитатором,
      поэтому отсутствующий после settlement листинг можно будет объяснить и
      сетью, и другим фасилитатором. Нужен отдельный замер на Sepolia через
      фасилитатор Coinbase, из места, где его credentials разрешено держать;
      по контракту тестовый хост их не получает.
