# Модель интеграции мерчанта: синтез после спора и проверки

Рабочая модель, выведенная 2026-08-26 в споре двух позиций (Дмитрий:
management API + SDK, мерчант заливает каталог и подписывается на заказы; я:
мерчант выставляет живой каталог-порт, мы читаем) и проверенная опытом
крупных платформ (`12-big-players-merchant-integration.md`). Кандидат в
решение — ADR-0002 (proposed). Здесь — сама конструкция и аргументы; статус
решения смотри в `docs/decisions/`.

## Чем закончился спор

Обе исходные позиции умерли, и это видно по чужим шрамам. Манифест-файл
(моя первая версия) — вторая копия истины: цены Freeland пересчитываются от
евро-себестоимости, наличие живёт посекундно, файл протухает в момент
сохранения. Pull-порт, где мерчант обязан хостить каталог и приём заказов
(моя вторая версия), — это конструкция ACP/UCP, и она проверена рынком с
разгромным результатом: к марту 2026 нативный Instant Checkout собрал меньше
тридцати мерчантов Shopify при конверсии втрое хуже собственного сайта, и
OpenAI свернул ровно ту часть, где мерчант — сервер. Поверх этих протоколов
немедленно выросли посредники (Stripe ACS, Copilot через PSP), снимающие с
мерчанта роль сервера. Coinslot относительно x402 занимает структурно ту же
позицию, что ACS относительно ACP.

Сама развилка «push или pull» оказалась ложной с двух сторон. Наша
агентская поверхность — живые 402-эндпоинты, которые индексирует каталог, —
это pull в любом случае; вопрос только в том, чем она питается. А индустрия
единодушно разделяет данные по температуре: идентичность товара — всегда
push, свежесть — всегда отдельный механизм ближе к моменту оплаты.

## Модель

**Холодная идентичность — push.** Карточки заливаются через наш management
API (publish / unpublish / update), ошибки валидации возвращаются в ответе
того же вызова — лучший DX-паттерн из существующих. SDK оборачивает это в
несколько строк. Прецеденты: Stripe Products, Shopify productSet, фиды ACS.

**Горячие цена и наличие — quote-hook в момент покупки.** Для товаров с
динамической ценой мерчант отдаёт один крошечный эндпоинт «сколько это
стоит и есть ли сейчас»; значение хука приоритетнее снапшота в карточке;
ответ несёт отметку as_of, отличающую «проверил сейчас» от «отдал кеш». Для
статичных товаров хука нет — живёт цена из карточки. Момент проверки,
сдвинутый вплотную к оплате, — индустриальная константа (Stripe hook,
Shopify Storefront на чекауте, re-price у Amadeus/Expedia, POS-проверка
DoorDash с измеренным эффектом).

**Две политики отказа — осознанно разные.** Молчит quote-hook — провал
открытый: берём снапшот, продажа продолжается. Молчит решение о списании
(approval / fulfillment) — провал закрытый: отказ до списания, деньги агента
не двигаются. Раньше у нас это был один принцип «отказ до списания»;
разводим по образцу Stripe, иначе секундная недоступность мерчанта убивает
продажу, которую можно было честно провести по снапшоту.

**Заказы — очередь у нас, транспорты сменные над одним объектом заказа.**
Мерчант никогда не обязан хостить приёмник. Транспорта три, все равноправны:
подписка SDK-воркера (дефолт пилота; прецеденты зрелой модели — Salesforce
Pub/Sub с Managed Subscriptions, Slack Socket Mode, Temporal, Telegram
getUpdates), классический webhook для тех, у кого инфраструктура под него
уже есть, и курсорный дренаж для пакетной обработки (паттерн bulk-fulfill
Stripe ACS). Один канал не бывает единственным: Shopify, Amazon и Stripe
все трое дописали очереди поверх вебхуков и предписали reconciliation;
обратного движения в индустрии нет. Инфраструктуру очереди не перекладываем
на мерчанта — обязательный AWS-аккаунт с SQS у Amazon это самая критикуемая
часть его дизайна, наш SDK существует ровно затем, чтобы этой цены не было.

**Идентификаторы двойные с первого дня.** Наш каталожный id плюс
merchant_item_id — переносимый ключ мерчанта. Все четверо крупных решали
эту задачу постфактум отдельным полем (lookup_key, customId,
merchant_item_id); не повторяем их путь через боль.

**Котировка живёт ограниченное время.** TTL, поведение по истечении и
снапшот цены в квитанции — обязательные части контракта. У ACP и
Cryptorefills окна жизни котировки нет вовсе, и ровно поэтому у них не
описано поведение при отсутствии товара после оплаты — дыра, которую мы
закрываем по построению.

**Нагрузка на мерчанта — наша обязанность.** Троттлинг хуков делаем мы;
проактивно опрашиваем только позиции с признаками дефицита. У Freeland для
этого уже есть дешёвый сигнал providerAvailable.

**Качество свежести — число, а не слово.** До пилота фиксируем SLO вида
«доля покупок, упёршихся в отсутствие товара, ниже N%» (ориентиры: у Stripe
опубликовано 5%, у Amazon аналог жёстче — 2,5% отмен до выдачи).

**Остатки — закрытый вопрос.** Никто из четверых не ведёт остаток за
мерчанта; все спрашивают мерчанта в момент покупки. Источник правды об
остатке — мерчант через quote-hook; журнала остатков у Coinslot нет
(закрывает пункт 6 из `10-design-backlog.md`).

## Чего осознанно не делаем

Не отдаём свежесть краулеру — Google прошёл этот путь и получил зависимость
от чужой разметки, отдельный класс ошибок про пропускную способность
краулинга и механизм самоотключения при расхождениях; хук по конкретному
товару дешевле и точнее. Не делаем доставку заказа одноканальной. Не строим
«несколько моделей интеграции» — модель одна, сменные только транспорты.
Не требуем от мерчанта хостить каталог или приёмник заказов; кто хочет
отдавать нам фид по расписанию — это ещё один способ доставки push-данных,
не вторая модель.

## Открытое, что эта модель не решает

- Машина состояний заказа: sync / async / confirm-first в терминах очереди
  и хуков; где в ней живёт подтверждение человеком. Следующий слой дизайна.
- Направление события заказа: у ACP/UCP мерчант шлёт события платформе, у
  нас платформа мерчанту. Если однажды станем транзитом в те протоколы,
  направление обернётся — ядро не привязывать к одному направлению.
- Подписи и авторизация management API, хуков и воркера.
- Числа: TTL котировки, SLO свежести — до пилота.
- Расхождение как штатное событие в ответах покупателю (паттерн
  quantity_adjusted у Shopify) — в дизайн ответов агенту.

## Связки

Идея «листенер хостим мы» впервые появилась из вскрытия смертей OpenBazaar
и Nostr-маркетплейсов (`06-prior-art-web2.md`, §3) — мерчантский листенер
их убил. Идемпотентность и режимы выдачи — `05-merchant-contract.md`;
модель Freeland с её Idempotency-Key и providerAvailable ложится без зазора
(`11-freeland-api-facts.md`). Доказательная база модели —
`12-big-players-merchant-integration.md`.

Расхождение с видением: фраза «есть API — подключение делаем мы, ваш код не
меняется» остаётся верной для консьерж-режима (воркер пишем и хостим мы),
но в самосервисе инженер пишет хендлер сам. После принятия ADR-0002 видение
уточняется явно, не молча.
