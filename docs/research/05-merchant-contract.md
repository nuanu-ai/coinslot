# Продуктовый дизайн: контракт и UX мерчанта

Сессия 2026-08-25, трек A. Основа — находки спайка
(`04-spike-bazaar-listing.md`) и ландшафт (`02-agentic-storefronts.md`).
Статус: проработка к ADR-0002/0003, решения не приняты.

## Принцип

**Мерчант описывает, ЧТО продаёт. Coinslot решает, КАК это продаётся
агентам.** Всё, что может измениться со стороны экосистемы (wire-формат,
каталоги, фасилитаторы, версии протокола), — за интерфейсом Coinslot и не
касается мерчанта. Проверено жизнью: миграция x402 v1→v2 заняла у нас час и
не тронула бы ни строчки мерчантского кода.

## Контракт мерчанта — три артефакта

1. **Манифест каталога** (`coinslot.yaml`, декларативный):
   - SKU: id, название, описание (англ., ≤500), схема входа/выхода
     (JSON Schema + примеры), метод;
   - цена: `fixed: 5.00 USD` **или** `quote: https://merchant/quote`
     (динамические цены — first-class: у Freeland eSIM/номера считаются
     cost+markup);
   - идентичность: serviceName (ASCII ≤32), tags (≤5), иконка.
2. **Один fulfillment-endpoint**: `POST /fulfill` c телом
   `{sku, params, payment_proof, idempotency_key}` → `200 {result}`.
   Подпись запроса Coinslot (HMAC или mTLS). Идемпотентность обязательна
   (повтор с тем же ключом = тот же результат, не вторая выдача).
3. **payTo** — кошелёк мерчанта. Деньги идут agent → merchant напрямую,
   Coinslot non-custodial.

Чего мерчант НЕ делает: x402, 402-ответы, verify/settle, фасилитатор,
discovery-метаданные, health/пульс, версии протокола, каталоги.

## UX-путь: onboarding инвертирован (питч 2026-08-25)

«Заполни манифест, напиши endpoint» — слишком сложно как первая фраза.
Инверсия: **манифест пишем мы, мерчант только апрувит.**

Питч инженеру Freeland: *«Ничего не пиши. Дай нам (1) кошелёк и (2) доступ к
вашему API для бекенд-интеграции. Мы сгенерим витрину из ваших доков — у вас
уже есть agent-facing SKILL.md, — покажем в песочнице, ты нажмёшь approve.
Ваш код не меняется вообще.»*

Механика: onboarding-агент Coinslot читает доки/OpenAPI/скилл мерчанта →
драфтит каталог (SKU, цены, схемы, описания) → маппит fulfillment на
**существующие** API мерчанта (адаптер на нашей стороне, авторизация — та,
что мерчант выдал нам) → песочница → merchant review → go-live.

Три тира мерчантов по трению:
1. **API-first** (Freeland): zero code — нужны кошелёк + credential + approve;
2. **Есть продукт, нет машинного API**: единственный код — один
   fulfillment-endpoint (наш SDK/шаблон);
3. **Полностью ручные** (web2 без API): очередь заказов/webhook — не пилот.

Манифест остаётся как артефакт (source of truth, версионируется, мерчант
может править сам) — но это результат onboarding'а, а не входной билет.

## Payment-грабли, которые закрываем дизайном сейчас

- **Идемпотентность выдачи**: оплата прошла, fulfillment упал → retry по
  idempotency_key, evidence-журнал, ручная развязка в операторке. (Дизайн
  Freeland-овских payment_checkouts — образец: fail-closed, snapshot цены.)
- **Динамические цены**: quote живёт ограниченное время (TTL), 402 отдаёт
  цену на момент запроса; фиксируем snapshot цены в момент settle.
- **Refund**: в x402 нативного refund нет. Политика пилота: продавать только
  идемпотентные цифровые ресурсы; refund-механика — backlog.
- **Мёртвый fulfillment**: 402 продолжаем отдавать (листинг жив), но
  отказываем ДО settle — агент денег не теряет, делистинга нет. Доступность
  листинга и честность продажи разведены.

## Расширение каналов экспонирования

Внутренний каталог = source of truth; каналы = **exposure-адаптеры**:

| Канал | Стоимость добавления | Когда |
|---|---|---|
| CDP Bazaar (+Agentic.Market, AWS/Cloudflare/Vercel агенты) | сделан (спайк) | пилот |
| Binance B402 | низкая: совместимый blob, но их фасилитатор/BSC | после пилота |
| MCP-сервер (x402-mcp) + каталог Anthropic | низкая: tools из тех же SKU | кандидат №2 |
| Фиды ассистентов (OpenAI/Google/UCP) | высокая: карточные рельсы, другой мир | по спросу |

Решение сейчас — только слой адаптеров в архитектуре, не сами адаптеры.

## Идентичность мерчанта в каталогах (multitenancy)

Каталоги индексируют ресурсы; идентичность продавца = домен + serviceName +
payTo. Два из трёх уже мерчантские (serviceName=«Freeland», payTo=кошелёк
мерчанта — виден как продавец в x402scan). Лестница по домену:

1. один домен Coinslot (сейчас, спайк);
2. поддомен на мерчанта: `freeland.<coinslot-домен>`;
3. **CNAME white-label**: `pay.mf0.store` → инфраструктура Coinslot; мерчант
   для каталога выглядит полностью собой, Coinslot невидим (модель Shopify).

Открытый вопрос к спайку: что ранкер Bazaar считает «shared domain» — от
этого зависит ступень по умолчанию.

## Операционные обязанности Coinslot (recurring-ценность)

- пульс листинга: ≥1 settle / 30 дней (self-settle $0.001 при отсутствии
  органики) — иначе автоделистинг;
- выживание health-probes; SLA-мониторинг fulfillment мерчанта;
- миграции протокола/каталогов за всех мерчантов разом;
- качество метаданных (находимость = качество description для intent-поиска).

## Входной гейт («CI для листинга»)

1. **Линт манифеста**: ASCII/лимиты (32/5/500), полнота схем (агент должен
   суметь составить валидный вызов), санитарность цены. Ловит всё, что
   каталог режет молча.
2. **Официальный validate** CDP по каждому ресурсу (бесплатно, без ключа).
3. **Тестовая покупка**: onboarding завершается автоматическим e2e settle;
   без него листинг в паблик не уходит.
4. **Комплаенс**: KYT-проверка payTo мерчанта (мы живём под OFAC/KYT
   скринингом CDP — грязный кошелёк мерчанта = риск всей платформы).
